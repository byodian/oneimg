# Social Share Set — issue #40

Implementation baseline: 4769626. This slice adds a local Studio sharing flow on ordinary Document Pages. The original Document remains in Recent Documents when a previewed Conversion Draft is saved as an independent Document.

## User behavior

- “拼成一张” composes up to nine photos and authored text on one Bounded Page. “成组分享” initially separates photos into ordered same-format Pages, retaining Media Item identity, caption, alternative text, crop parameters and source order. Existing share sets retain manual Page boundaries during subsequent format conversions.
- The declared formats are square 640 × 640, portrait 640 × 800 and story 630 × 1120. Story dimensions are exactly 9:16; the legacy/general presentation registry remains unchanged. Changing format creates another previewable copy instead of overwriting the source.
- Once a share Document is saved, multi-file addition fills the current Page up to nine photos and inserts further Pages immediately after it. The general long-image importer retains its existing nine-photo group boundary. The share inspector exposes previous/next/numbered Page moves and “从这里分页”; these work on touch devices without requiring drag. A split retains source reading order and following Blocks. Moving the last photo removes an empty source Page; a group caption is retained as ordinary text. A destination group keeps its existing Featured assignment when groups merge.
- Each add, transfer or split is one Document Core intention, one history step and one durable commit. Cross-page controls restore a useful neighboring focus target and announce the result, including after resource reloads. Page navigation selects the Page for editing and PNG export. Clipboard and system sharing explicitly name the current Page.
- PNG is always the initial format. JPEG/WebP appear only when a real Worker encoding probe returns the requested MIME. Selecting lossy quality invalidates the old proof. The actual final Blob is decoded, displayed with its byte size, and reused for download and system share; the ordered ZIP reuses these options and cached bytes. Clipboard uses only the current Page PNG. Unsupported sharing leaves current-page download available.

## Rendering, compatibility and ownership

The new oneimg-social-collage@1 Style Pack extends the existing CSS with social-only bounded geometry. Existing oneimg-foundation@3 CSS and legacy rendering stay unchanged. Social image frames clip crop/zoom transformations while captions remain measurable for overflow checks. Preview and Local SVG export select the same pack. The adapter accepts only known theme/density, social scene/template versions, canonical-renderer@3 and the pinned Noto font pack; unknown versions fail with a visible message rather than being silently certified.

An empty Page within a meaningful Document receives a quality warning; an entirely empty Document remains blocked. Every Page passes the existing RenderReady and Export Preflight interfaces, including resource resolution, meaningful content, overflow, font fallbacks and the browser capability probe. Export plans carry the resulting findings. Sensitive content stays local. JPEG/WebP run in an owned Worker over an already canonical PNG, with cancellation, a timeout and worker/object-URL cleanup. Format probes are aborted on dialog disposal. Encoded and PNG caches retain at most eight entries each. ZIP is generated incrementally with STORE entries and supports cancellation; exhaustive large-document memory measurements remain tracked in #66.

Asset Pipeline normalization provides the shared orientation-correct Render Source; output encoders never read Asset Originals. Raster output excludes source EXIF, location, device and file-name metadata. Filenames combine a cleaned short Document name, local calendar date and padded Page sequence (for example oneimg-2026-09-14-page-001.png). Sensitive Documents start with a neutral name; an explicit export-name field allows renaming without altering authored content. PNG, JPEG and WebP extensions match their bytes. Bundle entries follow current Page order, with a fixed ZIP timestamp.

Browser behavior follows [OffscreenCanvas encoding](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas/convertToBlob), [Clipboard MIME support](https://developer.mozilla.org/en-US/docs/Web/API/ClipboardItem/supports_static), and [user-activated file sharing](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share). Silent fallback to PNG is rejected for requested JPEG/WebP. The UI invokes system sharing only from an explicit user click after canShare accepts the actual file; no social-account publishing is performed.

## Evidence and remaining gates

Scenario coverage in tests/scenarios/social-share.spec.ts exercises conversion/source preservation, serialized round trips, current-page raster geometry, CJK captions, preview-to-PNG pixel comparisons for each declared format, actual JPEG/WebP byte reuse, ordered ZIPs, clipboard and Web Share API boundaries, capability failure, narrow viewports, cancellation, multi-file overflow, cross-page edits and history/reload recovery. Platform sharing calls are replaced by boundary doubles so tests do not write to a real clipboard or invoke the host share sheet.

Final review, full-suite and build results are recorded in issue-delivery-status.md and the remote issue comment after verification. Chromium scenario evidence does not close the representative-device/cross-browser conformance gates in #59 or the broader export stress matrix in #66.
